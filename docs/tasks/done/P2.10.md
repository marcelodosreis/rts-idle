## Task

- ID: `P2.10`
- Objective: Enable a pawn to repair owned mechanical units and completed mechanical buildings through the authoritative command and browser flow.
- Why: Restore damaged mechanical assets without introducing non-deterministic or UI-owned gameplay state.
- Scope: shared command contracts, protocol validation, simulation repair order/system/rules, game-data mechanical tags, server regression scenario, snapshot projections, renderer/HUD interaction, and Playwright coverage.
- Non-goals: repair of non-mechanical entities, allied/enemy repair, multiple simultaneous repairers per target, research/modifiers, pathfinding, or economic rebalance beyond the repair constants.

## Contract

- `REPAIR` carries `{ unitIds, targetId }`; the authoritative handler validates the issuing player owns the selected entities, then chooses only the lowest entity ID among selected pawns as the repairer.
- The target must be owned by the same player, alive, damaged, and tagged `mechanical`; the repairer must be a pawn. Invalid targets or selections reject atomically.
- A target has at most one active repair order. A second repair command for the same target is rejected.
- Repair uses centralized rules: `REPAIR_TICKS_PER_STEP = 10`, `REPAIR_HP_PER_STEP = 5`, and `REPAIR_MINERAL_COST = 1`. Every 10 simulation ticks at the target, it spends one mineral and restores up to 5 HP. A final partial repair still costs one mineral. With no mineral, it stops without healing.
- The repair order resolves when the target is full, dead, invalidated, or resources are unavailable. `STOP` cancels it without refund.
- Mechanical tags are explicit in authored unit/building definitions. Current pawns, warriors, archers, Base, Barracks, and Supply Depot are mechanical; future non-mechanical content can opt out without changing repair logic.
- Canonical order serialization appends a new `REPAIR` tag; existing tags retain their numeric values. Snapshots expose `repairing` as an order state and retain authoritative HP.
- Browser flow: on the match screen, select one or more owned workers and right-click a damaged owned mechanical unit/building. The deterministic first pawn receives the order. The HUD/selection state shows repairing progress, current HP, and blocked completion/no-resource feedback. The real server path is covered by the regression scenario E2E.
- Determinism: same seed, snapshot, and command sequence produce identical state/hash; no client-side repair mutation is allowed.

## Design

- Repair constants live in one simulation rules module and are imported by validation/system tests.
- The command handler only validates and assigns the order; the repair system owns tick progression and resource/HP mutation.
- Mechanical eligibility is read from authored data, not inferred from UI labels or entity IDs.
- Domain variants use closed registries and exhaustive dispatch; protocol guards fail closed.
- The system is appended to the existing economy stage rather than reordering the frozen pipeline.

## Tests and validation

- Simulation: command admission, deterministic first-worker selection, ownership/tag/dead/full/duplicate rejection, 10-tick cadence, partial cost, no-resource stop, unit/building targets, and snapshot/hash continuation.
- Contracts: valid/invalid `REPAIR` wire payloads and `repairing` snapshot order state.
- Unit/UI: repair rules and interaction controller command selection/projection feedback.
- Browser: `tests/e2e/economy/scenarios.spec.ts` regression flow for Base damage from `500` to `250` and repair back to full, including visible progress and no-resource blocking.
- Validation commands: `pnpm run verify:simulation`, `pnpm run test:contracts`, `pnpm run test:e2e:focused tests/e2e/economy/scenarios.spec.ts --list`, focused E2E, `pnpm run verify`, and `pnpm run test:e2e:fast`.

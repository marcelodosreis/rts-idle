# Task Packet: P2.09.01 — Production Cancellation and Producer Cleanup

## Task

- ID: `P2.09.01` / master-plan deliverable `P2.09`
- Objective: let the owner cancel any not-yet-started production item and ensure producer removal releases all queued reservations without refund.
- Why: production currently locks minerals and supply until spawn, and a removed producer has no authoritative cleanup path.
- Scope: shared command contract, protocol guard, simulation command and lifecycle cleanup, canonical state/invariants, server projection if required by the queue shape, match HUD, focused unit/simulation/contract/integration tests, production E2E, and gameplay documentation.
- Non-goals: building combat or building health, demolition, cancellation of construction, cancellation of rally, queue reordering, production speed changes, new unit types, repair, research, multiplayer, or pathfinding.

## Contract

### Authoritative command

- Add a typed `CANCEL_PRODUCTION` command with payload `{ producerId, queueIndex }`.
- `producerId` and `queueIndex` are integer entity/index values; `queueIndex` is resolved against the canonical queue at command application time.
- Only the active owner of an existing, completed `BASE` or `BARRACKS` may cancel production.
- `queueIndex` must address an existing item. Invalid producer, ownership, lifecycle, or index rejects atomically with the existing typed command rejection path.
- The command removes exactly one queue item and does not reorder the remaining items.
- If a queued, not-yet-started item is canceled, refund its full reserved mineral cost.
- Active and `COMPLETED_WAITING` items reject cancellation with `INVALID_STATE`.
- Release exactly one reserved-supply amount for every canceled queued item.
- Refund and reservation release happen atomically with queue removal. A rejected command changes nothing.
- The refund is credited to the owning player's mineral wallet; destruction never refunds production cost.

### Producer removal lifecycle

- Add one authoritative simulation-owned cleanup path for removing an entity that owns a `Production` queue.
- Before the producer is removed, release the full `reservedSupply` represented by every queued item to its owner.
- Discard the producer queue, rally point, and all other producer components through the existing entity-removal behavior.
- Do not refund minerals for queued, active, or completed-waiting items when the producer is removed.
- Route every authoritative producer-removal path through the cleanup helper, including the existing destruction/removal path and surrender cleanup where applicable. Do not rely on callers to manually adjust `reservedSupply`.
- Removing an entity without a production queue keeps its current behavior.
- The cleanup must be deterministic and safe when the owner or producer is already unavailable; impossible state must fail through invariants rather than silently creating or losing supply.

### Canonical state and invariants

- Queue order, item fields, player `reservedSupply`, and wallet balance remain canonical and snapshot/hash inputs.
- After cancellation or producer removal, the invariant must equal player `reservedSupply` to the sum of all surviving production items owned by that player.
- A producer with a queue remains a completed owned producer; no dangling queue or reservation may survive entity removal.
- Snapshot/restore and deterministic replay must preserve cancellation results, queue indexes, refunds, and post-removal supply values.
- Bump the simulation version and regenerate/update golden evidence only if the canonical schema or command registry requires it; do not change pinned serialization formats without the task's explicit test evidence.

### Player-facing flow

- Route: existing match screen, including `?scenario=default` production flow.
- When the player selects an owned completed Base or Barracks with a non-empty queue, each visible queued row exposes a cancel action identified by its current queue position.
- The action uses the existing two-step confirmation pattern used by construction cancellation. The confirmation displays the expected full mineral refund for queued rows.
- On confirmation, the client sends `CANCEL_PRODUCTION` through the existing authoritative WebSocket command path. Active and completed-waiting rows have no cancel action.
- The HUD immediately reflects the authoritative snapshot: queue count, row positions, training status, minerals, and reserved/used supply.
- Canceling a middle or last queued item leaves the remaining order unchanged.
- A producer with no queue shows no cancellation controls. A stale selection, enemy producer, foundation, paused construction, Supply Depot, invalid index, or removed producer does not expose a usable action; the authoritative rejection/snapshot path leaves the UI consistent.
- Browser coverage must exercise the real server path, not a mocked command sender.

## Design

- Keep command validation and mutation in a dedicated simulation command module, following the existing `TRAIN` and `CANCEL_CONSTRUCTION` split.
- Keep refund calculation as a pure shared helper with named constants and integer arithmetic; reuse the construction refund style only where the formula is identical, without coupling construction and production domain modules.
- Keep producer reservation cleanup in a small simulation lifecycle helper called by authoritative removal sites. `World.removeEntity` remains a storage primitive and does not receive player/economy policy.
- Extend the shared command registry once, add a typed protocol guard, and use exhaustive dispatch with `assertNever` where required. No loose command strings or `Record<string, X>` domain maps.
- Preserve the frozen pipeline order, sorted entity iteration, single-writer `step()` rule, and read-only server/web projections.
- Extend the existing production panel rather than introducing a second queue model. The queue index is presentation-derived from canonical order and is sent only after explicit confirmation.
- Keep the E2E scenario small: one producer, at least three queue entries, cancellation of active/middle/last entries, and a producer-removal fixture for cleanup. Do not add building combat to make destruction player-driven.

## Implementation slices

1. **Contract slice:** register `CANCEL_PRODUCTION`, define its payload, protocol decoding/validation, command dispatch, and rejection cases.
2. **Refund slice:** add the full queued-item refund rule with focused unit tests.
3. **Simulation slice:** remove an arbitrary queue index atomically, promote the next item when required, update minerals and reserved supply, and preserve canonical round-trip/hash behavior.
4. **Lifecycle slice:** centralize producer queue cleanup and route producer removal/surrender through it; add invariant and integration coverage for destroyed queues.
5. **Projection/UI slice:** expose enough authoritative queue data for row-level cancellation, add confirmation/refund feedback, send the command, and handle stale/blocked states without optimistic mutation.
6. **Browser slice:** cover queued middle/last cancellation and wallet/supply feedback through the economy scenario and real server.
7. **Documentation slice:** update `docs/commands.md`, `docs/simulation.md`, `CURRENT_STATE.md` only at milestone completion, and the phase task indexes.

## Risks and rollback points

- **Command schema/version risk:** adding a command or changing canonical state can affect protocol and golden hashes. Roll back at the contract slice if guards or round-trip evidence diverge.
- **Reservation leak risk:** route all producer removal through one helper and assert the reservation sum after every affected simulation test. Roll back before UI work if this invariant is not stable.
- **Queue-index race risk:** resolve the index only when the authoritative command executes and render from the next snapshot. Never identify an item by a client-generated mutable ID.
- **UI stale-selection risk:** treat a missing producer/queue row as a no-op in the UI and rely on authoritative rejection for races; do not add optimistic bookkeeping.
- **Scope risk:** if building destruction requires new combat semantics, stop and open a separate Phase 3 task instead of expanding P2.09.01.

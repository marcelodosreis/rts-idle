# P3.03.01 - Footprint Navigation Invalidation

## Task

- ID: `P3.03.01`
- Objective: keep navigation footprints synchronized with authoritative building lifecycle and invalidate stale searches deterministically.
- Why: construction sites and buildings must block paths before movement can safely use the navigation result.
- Scope: simulation navigation state/system, building lifecycle integration, canonical snapshot/hash versioning, and focused simulation/integration tests.
- Non-goals: collision radii, mobile-unit avoidance, group formations, vision, protocol feedback, renderer changes, or browser gameplay.

## Contract

- Static navigation blockers come from the canonical map/grid definition; dynamic blockers come from every authoritative building footprint, including constructing buildings.
- Footprints are rectangular, row-major, and deterministic. The navigation grid must include every footprint tile and must never block unrelated tiles.
- Construction admission, cancellation, completion, and entity destruction are reflected by the next navigation substep in `orders`.
- A changed footprint rebuilds only the derived navigation grid and preserves the static grid definition.
- Pending or already-found searches are conservatively invalidated with `NAVIGATION_CHANGED` whenever the dynamic footprint set changes; no stale route may continue across a changed grid.
- Invalidated searches retain their request identity and expansion count, expose the tick of invalidation as `availableTick`, and do not receive further budget.
- Static and current grid definitions, requests, cursor, and invalidation results are canonical snapshot/hash state.
- Snapshot restore and deterministic replay preserve footprint state, invalidation status, and tick ordering.
- Only `step()` and its systems mutate navigation state; pathfinding remains a pure package boundary.

## Design

- `NavigationState` stores a serializable static definition and current definition plus a non-enumerable derived `NavigationGrid` runtime object.
- `navigationSystem` derives building tiles from the ECS `Building` component at the existing `orders` substep, updates the grid, invalidates affected in-flight results, and then advances the bounded scheduler.
- Building lifecycle code remains authoritative in commands/systems; navigation observes the resulting ECS state rather than creating a second building model.
- Closed domain statuses use existing `as const` registries and exhaustive dispatch. No protocol or renderer dependency is introduced.

## Player-facing completion

- This is an authoritative navigation foundation. Blocked/unreachable feedback and player-facing movement belong to the later movement slice.

## Acceptance and stop conditions

- [ ] Building footprints are synchronized before navigation advances.
- [ ] Construction, cancellation, completion, and destruction have regression coverage.
- [ ] In-flight stale searches become `INVALIDATED` deterministically.
- [ ] Snapshot/hash/replay and architecture gates pass.
- [ ] Stop before collision, group destinations, or UI work.

# P3.10.01 - Projectiles

## Task

- ID: `P3.10.01`
- Objective: Replace applicable instant ranged damage with authoritative, observable projectiles.
- Why: Ranged combat needs readable travel, impact, dead-target, and expiry behavior.
- Scope: `packages/game-data`, `packages/shared`, `packages/protocol`, `packages/simulation`, `apps/server`, `packages/renderer`, `apps/web`, and E2E tests.
- Non-goals: Area damage, new faction systems, terrain interception, and AI.

## Contract

- Projectile creation, movement, impact, dead-target handling, and TTL are deterministic and snapshot-safe.
- Homing and hidden trajectory data remain server-private; the client receives only the observable segment.
- Terrain does not intercept projectiles in the MVP, as defined by the master plan.
- Only `Archer` uses a projectile in this task. `Pawn`, `Warrior`, and `Lancer` keep their current instant damage behavior.
- Archer projectile speed is `10 tiles/s` and projectile TTL is `20 ticks` at the authoritative 20 ticks/s simulation rate.
- An out-of-range `ATTACK` continues to pursue normally; a projectile is created when the Archer reaches attack range.
- Projectile advancement remains inside the existing combat system so the frozen pipeline is not reordered or extended.
- Damage is captured when the projectile launches and target armor is evaluated at impact. A projectile continues after its Archer source dies.
- Natural interaction: select a ranged unit and issue an attack against a visible target.
- Success feedback: the player sees projectile launch, travel, impact, and resulting damage.
- Blocked/error feedback: hidden, dead, and expired targets produce readable non-damage feedback. Out-of-range targets remain pursuit, not rejection.
- Browser target: `tests/e2e/match/projectiles-playable.spec.ts` through the real server.

## Design

Keep projectile state in simulation and project only observable data. Preserve the frozen system order, canonical snapshots, typed projectile tags, and renderer ownership of animation.

### Authoritative lifecycle

- Existing projectiles advance in ascending `projectileId` order before new attacks create projectiles.
- A projectile created in the current tick does not move until the next tick.
- Homing reads the current target position while the target is alive; hidden-to-client target data remains server-private.
- If the target is removed before impact, the projectile travels to its last known position and expires without damage.
- An impact adds damage to the existing per-tick damage buffer, removes the projectile, and can only happen once.
- Projectiles that do not impact decrement TTL; zero TTL removes the projectile without damage.
- Fixed-point speed uses integer division and a persisted remainder so projectile
  definitions that do not divide evenly by the 20 ticks/s rate remain deterministic.

### State and wire shape

- Canonical simulation state contains `projectiles` and `nextProjectileId`.
- Private state stores source, target, last-known position, captured damage, TTL, and fixed-point movement remainder.
- Public `SnapshotProjectile` contains only `id`, `kind: 'arrow'`, `owner`, `x`, and `y`.
- Snapshot deltas carry projectile upserts and `removedProjectileIds`.
- Lifecycle events carry projectile ID, kind, position, and expiration reason, never target ID or private trajectory.
- Projectile observations are filtered by the player's current visible tile; hidden projectiles are removed from the client view.
- Simulation version advances from `0.25.0` to `0.26.0`; protocol version advances from `0.9.0` to `0.10.0`.

### Player-facing slice

- Add a dedicated `projectiles` demo scenario with a player Archer and a visible enemy target in range after the player issues `ATTACK`.
- Keep the existing targeting scenario for the loss-of-vision and hidden-target rejection path.
- Render the faction Arrow asset with a deterministic geometric fallback and interpolate only between observed positions.
- Place projectile presentation between units and fog so only observed projectile positions are rendered.

## Tests and validation

- Unit and simulation tests for creation, movement, impact-once, dead targets, TTL, and serialization.
- Unit and simulation tests cover Archer death during flight, fixed-point remainder movement, deterministic projectile ordering, and multiple impacts in one tick.
- Protocol and server tests cover snapshot guards, delta removal, observation hashes, and hidden projectile filtering.
- Renderer tests cover asset fallback, interpolation, removal, impact, and expiration presentation.
- Determinism and replay tests for projectile sequences.
- Browser E2E in Chromium and Firefox covering launch, travel, impact, and blocked shots.
- `pnpm run verify`

# P2.12 — Economic Integration

**Status:** done
**Phase:** Phase 2 / economy and production
**Dependencies:** P2.01–P2.11, QH.28.01

## Objective

Prove the complete authoritative economy chain from resource gathering through
Castle II, Monastery production, and research in one real-server player flow.

## Why

The individual economy capabilities are playable, but no single regression
proves that their state transitions compose without pre-seeded progression.

## Scope

- `tests/e2e/economy/economy-chain.spec.ts` for the player-facing flow.
- Integration or determinism coverage for the composed server session where
  existing lower-level tests do not prove the transition.
- This packet and Phase 2 status documentation.

## Non-goals

- New economy commands, resources, buildings, units, research, or modifiers.
- Balance changes beyond what is required to make the existing regression flow
  observable and deterministic.
- AI, pathfinding, collision, multiplayer, or unrelated HUD redesign.

## Contract

The player opens `/?scenario=regression&aggression=passive` and uses only the
match HUD and canvas interactions. The authoritative sequence is:

1. Select an owned worker, gather Gold from the map-authored Gold Mine, and
   observe the worker reach `Harvesting` with carry feedback.
2. Send the worker to the owned Castle and observe the deposit increase the
   Gold wallet through the server path.
3. Upgrade the owned Castle from Tier I to Tier II and observe progress and
   completion in the construction panel.
4. Build and complete a Monastery at a valid map location, then select it and
   observe both Train and Research actions.
5. Queue a Monk and Economy research in the shared Monastery queue. Observe
   the Monk production row, research row, progress, completion feedback, and
   the Economy effect on a selected Pawn's cargo capacity.

The server remains authoritative. Browser code must not mutate simulation state
directly. The flow uses the deterministic `regression` fixture, semantic entity
lookup, authoritative ticks, and observable HUD state. Insufficient-resource,
invalid-placement, and locked-tier behavior remain covered by the existing
focused tests and are not redefined here.

The composed command stream must preserve snapshot independence and produce the
same final state/hash when replayed with the same seed and commands. No public
wire or canonical serialization format changes are permitted.

## Design

- Reuse existing E2E support helpers and the existing match HUD; do not add a
  second progression fixture or debug-only gameplay path.
- Keep progression setup in the browser test as natural selection and command
  interactions. Use debug observation only to locate semantic entities and
  poll authoritative state.
- Keep any composed simulation assertion in integration/determinism tests and
  use existing command/session boundaries rather than mutating ECS stores.

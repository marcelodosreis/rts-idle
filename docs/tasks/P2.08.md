## Contract

- `RALLY` carries `{ producerId, x, y }` in fixed integer coordinates.
- Only an owned, completed `BASE` or `BARRACKS` accepts `RALLY`; invalid commands reject atomically.
- Each producer has `rallyPoint: { x, y } | null`; setting a point replaces the previous point.
- A missing rally leaves spawned units idle. A configured rally applies a normal movement destination when the unit spawns.
- The deterministic exit remains the current east/top exit. If it is outside the map, invalid, inside another building, or occupied by a live unit, the completed item remains `COMPLETED_WAITING` with minerals and supply reserved.
- The system retries the same exit on later ticks and releases the reservation only after a successful spawn.
- Rally changes while an item waits affect that item when it eventually spawns.
- `rallyPoint` is canonical state and is projected as nullable in `SnapshotBuilding`.
- The production panel exposes `Set rally` only for an eligible selected producer, shows the authoritative rally point, and displays blocked completion status.
- Browser E2E covers selecting a producer, setting rally, training, spawn movement, and blocked-exit recovery through the real server.

## Design

- Keep authority in simulation `step()` and use the existing movement destination component instead of adding a persisted rally order.
- Extend the shared command registry and protocol guard; use typed `CommandMode` data for the selected producer.
- Keep server projection read-only and render a lightweight rally marker from the snapshot.
- Preserve the frozen pipeline order and deterministic entity-id iteration.
- The canonical schema changes deliberately require a simulation version bump and updated golden evidence.
